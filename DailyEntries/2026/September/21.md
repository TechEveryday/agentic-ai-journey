## Context and Planning

There was no session plan for today. This entry is a reconstruction from commit history after the fact, which is itself the main process observation of the day (see Reflection).

The work clusters into two unrelated motivations:

1. **A hard external deadline.** App Store Connect requires a reachable privacy policy URL and support URL before a build can be submitted. My Assistant Coach (`TechEveryday/my-sport-assistant`) is private, and a free-plan GitHub org **cannot serve Pages from a private repo**. The pages had to be hosted somewhere public, so the LLC site became the host.
2. **A reaction to reading the sites.** The remaining four commits read like someone loading both homepages, noticing they were repetitive, and editing until they were not. Each commit message argues a specific redundancy rather than a taste preference — that is why they are worth keeping in the log.

### Key Decisions

- **Publish the app's legal pages on the LLC site, not the app repo** - The app repo is private and cannot serve Pages on a free org plan. The commit records the two live URLs, so the App Store submission has something stable to point at.
- **Keep the source of truth in the app repo** - The policy still lives in `TechEveryday/my-sport-assistant` under `docs/`; the LLC site holds a copy to be refreshed when the policy changes. Deliberate duplication with a documented direction of flow, not an accident.
- **Static HTML with zero scripts and zero external requests** - Stated in the commit as a principle: *"a privacy policy that promises no tracking must not load anything from anywhere."* No fonts from a CDN, no analytics, no framework. The page's own network behavior has to match its claims.
- **Name the players-data question instead of hiding behind "we collect no data"** - The policy has a dedicated section on roster data, explicitly because the names typed into a youth-sports app are usually children's. "Data Not Collected" is true at the App Store label level and still not the whole answer.
- **Delete content rather than restyle it** - Every one of the four site-polish commits removes something. No commit today added a new section to either homepage.
- **Move the `#about` anchor rather than drop it** - Both LLC commits that dissolved the About section explicitly relocated `id="about"` so existing nav links and any inbound deep links keep resolving. This is the kind of detail that silently breaks and nobody notices for months.

## Technical Implementation

### The pattern behind the LLC consolidation

Nothing was restyled. The edit was structural, and the rule it followed is a content rule, not a CSS one:

> A card earns its place only if it states a fact the prose does not.

Applied to eight cards, four failed. *Based in: Minnesota* duplicated the hero kicker ("Full-stack software studio · Minnesota"). *Focus: Full-stack* duplicated the headline. *Entity: Tech Everyday LLC* duplicated the brand. The bento's lead card duplicated the lede. All four went. This is a rule you can apply to a page in a few minutes, and it does not need a redesign.

### Hand-maintained ordinals make reordering a multi-file edit

The personal site numbers its section headings by position, and stores each number as a literal string inside the component that renders it:

```vue
<!-- src/components/StackSection.vue -->
<SectionHeading label="01 - Skills &amp; tools" />
```

Moving one section therefore touches **five files**: `App.vue` for DOM order, `profile.ts` for nav order, and one edit inside each affected section component to renumber it. Nothing enforces that the labels stay consistent with the actual order — a reorder that forgets one component produces a page numbered `01, 01, 03` and still builds, still passes type-check, and still deploys.

Both of today's commits got it right. The structure is what makes getting it wrong easy:

```ts
export const navLinks: NavLink[] = [
  { label: 'about', href: '#about' },
  { label: 'stack', href: '#stack' },      // nav order
  { label: 'experience', href: '#experience' },
]
```

The order is already declared here. Deriving both the DOM order and the heading numbers from one list would make the reorder a one-line change and the inconsistency unrepresentable. Filed as a next-session item.

### Anchors outlive the sections that owned them

Both LLC commits dissolved a block that owned `id="about"`, and both moved the id onto whatever replaced it rather than dropping it. That keeps the header nav working and keeps any external `#about` link resolving. Worth stating as a rule: **when a section is deleted, its anchor is part of the site's public surface** — reassign it, don't delete it.

## Lessons Discovered

No new file in `lessons/` today — but two candidates, both concrete:

- **CLAUDE.md's `.nvmrc` rule is not being followed outside this repo.** `CLAUDE.md` says every project must pin Node 20.11.0+ in `.nvmrc`. `techeveryday.github.io` has **no `.nvmrc` at all**, and `viraphilavong.github.io` pins the bare string `20`, which satisfies "Node 20" but not the stated 20.11.0 floor. Both deploy workflows hardcode `node-version: 20` instead, so the pinned version lives only in CI and a local `nvm use` does nothing. The rule exists because of `lessons/git-workflow-and-node-versioning.md`; it was written for `projects/` and never applied to the two repos that are actually in production.
- **"Looks right in git" is not "is deployed."** Putting the privacy pages at the LLC repo root would have produced a clean-looking commit that published nothing, because the deploy workflow ships only `te-website/dist/te-website` and the root bundles are stale artifacts of a previous deploy model. This is the same failure shape as `lessons/template-drift-and-broken-scripts.md` — config that reads correctly and does nothing when exercised. **Verify where a file lands in the build output, not where it looks right in the tree.**

## Reflection

### What Went Well

1. **The commit messages did the documentation's job.** Each one argues *why* — which three blocks said the same thing, why the Mobile chip had to go once two projects were removed, why the pages could not live in the app repo. This entry was reconstructable weeks later from history alone, which is the whole test of a commit message.
2. **Deletions were complete.** Empty filter chip removed with the projects that emptied it. Orphaned CSS (`te-bento`, `sp2`, `sp2r`) removed with the markup that used it, media queries included. Anchors relocated rather than dropped. The usual failure mode is removing the visible half and leaving the rest.
3. **The privacy policy is honest where it would have been easy not to be.** "Data Not Collected" is accurate for the App Store label, and the policy still spends a section on the fact that users type children's names into the app. That is a deliberate choice to answer the question a parent would actually ask.
4. **Blocking work got done first.** The App Store dependency landed at 15:12, before any of the cosmetic edits. Right order.

### What Didn't Go Well

1. **The personal site's reorder took two commits to land one decision.** #11 put Skills & tools first; #12 put it back under About ten minutes later. The reasoning in #12 ("open on who I am before what I work with") would have been just as available before #11. Cost was trivial here — two 5-line commits — but the pattern is *edit, look, re-edit*, and the LLC page shows the same shape: #16 moved About into the hero, #17 rewrote that same block twelve minutes later.
2. **No session plan, so this entry is archaeology.** Day 5's entry was written alongside the work with decisions recorded as they were made. Today's was reconstructed from `git log` hours later. It was recoverable only because the commit messages were unusually good — that is luck to be depending on, not process.
3. **The live URLs still have not been hit.** The entire reason `641919d` exists is that App Store Connect needs two reachable URLs. Nothing today confirmed either of them responds with HTTP 200.
4. **Both production sites violate the repo's own Node rule** (see Lessons). The standard is written down and enforced nowhere outside `projects/`.

### Technical Insights

- **Consolidation is a content problem before it is a design problem.** Nothing on the LLC page was restyled. Eight cards became four and three blocks became one purely by asking which of them stated a fact the prose did not already state. No new component, no new CSS.
- **Duplicated ordinals are a correctness hazard.** `01 -`, `02 -`, `03 -` hardcoded into three separate components means the numbering can disagree with the DOM order and nothing catches it — not the type-checker, not the build, not the deploy. The order is already declared once in `profile.ts`; deriving the labels from it would make the bug unrepresentable.
- **Anchor ids are public API.** They sit in nav links, bookmarks, and anything anyone ever pasted. Deleting a section is not license to delete its id.
- **A static page can be a feature.** Three files with no framework, no scripts, and no external requests unblocked an App Store submission. The correct amount of tooling was zero, and the "no external requests" constraint was load-bearing rather than minimalism for its own sake.
